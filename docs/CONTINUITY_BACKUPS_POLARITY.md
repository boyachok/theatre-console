# 0.7.13 — инверсия PWM, непрерывность сцен, версии и JSON (НЕ прошита)

Версия подготовлена программно. В театре ещё нужны отдельно авторизованная
прошивка совместимых master/slave и физическая проверка выходов. Платы,
действующая партитура, LIVE и привязки при разработке не изменялись.

## 12 независимых инверсий PWM

«Приборы → Настроить прибор → Инвертировать DIM1…DIM12». Это **настройка
физического канала прибора**, общая для всех его сцен, не очередной эффект ячейки.
У новых приборов каждая галочка явно false. В JSON хранится `Parameter.inverted`.
Для helmet, реле и Диммер220 этой галочки нет; PSM остаётся активным HIGH.

В партитуре/preview/Runner значение всегда логическое:0=темно,255=полная яркость.
На последней ступени hardware write единожды применяется `255−logical` при
инверсии. Фейды, анимации, floor, light delay и STOP считают логические значения.
При инверсии логический OFF/STOP становится физическим255. Несущая всех12 остаётся
25кГц: первые8LEDC, последние4MCPWM, включая постоянные крайние уровни.

### Старая NVS и замена платы

Раньше инверсия уже существовала в низкоуровневом NVS `pwmConfig`, только для
первых8. В старых проектах поля `inverted` нет: это **не приказ сбросить NVS**.
Wire различает `invertedMask` и `inversionSet`: незаданные биты оставляют настройку
платы, явные false/true её задают. Никакого двойного XOR двух инверсий.

Новый атомарный16B NVS record `dimConfig` содержит12бит инверсии и прежние8presets.
На boot он предпочитается старому; при отсутствии берутся прежние settings.
Старый `pwmConfig` не стирается/не переписывается миграцией. Новые настройки
сохраняются только при реальном изменении, не на каждом RUN/tick/сцене.
Legacy PWM_CONFIG также обновляет новый record. Откат на старый firmware видит
старые значения старого ключа: после изменения полярности это надо учитывать.

Редактор показывает полученную hardware-полярность для старых незаданных полей.
**Явное «Сохранить» в Приборах** переносит полученные от online-платы полярности
в проект/будущие JSON. Сама телеметрия и импорт старого JSON проект не меняют.
Если старая плата offline/сломана и значение никогда не было сохранено в проект,
его нельзя восстановить из отсутствующего поля: задайте вручную/из технического
бэкапа. Известные явные галочки не заменяются чужой телеметрией.

Сценарий замены: сохранить тот же Device ID и все сцены, заменить только MAC,
прошить совместимый slave, загрузить план с master. Явные настройки из JSON
применятся при принятии cue и сохранятся в NVS. Сам STORE только сохраняет план,
не является GO/применением полярности. Если драйвер active-LOW, пустую новую плату
сначала сконфигурировать без подключённой нагрузки: до первого cue она ещё не знает
эту полярность. На последующих boot она уже читает сохранённый record. Другие произвольные данные NVS/внешние SD-файлы JSON
автоматически не копирует. Полярность/неактивный уровень и переходы boot/reset
обязательно проверяются на конкретном драйвере без опасной нагрузки; software
инициализация не доказывает отсутствие электрических переходных импульсов.

## Отложенный свет = отложенный переход

Один GO может запустить звук сразу, а свет изменить через5с или другое время.
До deadline **продолжаются предыдущие яркость, фейд и анимация** канала. В deadline
из достигнутого на тот момент выхода начинается новый фейд и новая фаза анимации.
Работает и переход **в0**: прежний свет держится до задержанного fade-out.

Новый шаг/back задаёт новую задержку; retry не переносит её. LIVE-правки ожидающей
цели не прерывают старый сигнал и не сдвигают исходное время запроса; изменение
самой задержки пересчитывает deadline от него. Если срок уже прошёл, новый переход
начинается сейчас. Уже начатый переход не выключается от редактирования одного
delay. STOP/отключение модуля отменяют ожидание. Значения0–3600с, millis wrap-safe.

Ровно тот же подтверждённый cue при reconnect/recovery не перезапускает задержки,
фазы, реле или звук. Новый актуальный cue применяется обычным образом.
Нет общего executeAt, фазовой синхронизации плат или автоматического пролистывания
пропущенной истории. Времена — локальные, tick best-effort.

## Звук в обе стороны

-7→7 вперёд/back/FIRST/LAST/select/recovery: тот же файл продолжается, без нового
 STOP/PLAY, без сброса fade-in. Меняются запрошенная громкость/loop, если изменены.
-7→пусто→7 или7→8→7: возвращение к7 — новый запуск с его delay/fade.
-Если7 уже закончилось, навигация между одинаковыми7 не выдаёт фиктивный PLAY:
 оно остаётся завершённым. Новый файл/посещение пустой ячейки/явный STOP меняет
 состояние для следующего запуска.
-Если тот же файл ещё ждёт запуска, навигация в обе стороны сохраняет исходный
 запрос/deadline. Изменённый startDelay пересчитывается от исходного запроса,
 loop-edit перестраивает ещё не переданную транзакцию с тем же deadline.
-Между пустыми ячейками незавершённый fade-out тоже не начинается снова.
-Loop, mute→repeat→PLAY и якорь fade на actual UART TX сохраняются. TX/ACK не
 доказывают реально слышимый звук или поведение конкретной SD-карты/модуля.

## Пропала связь — держим принятое состояние

Никаких новых режимов/авто-blackout по Wi-Fi/master/remote loss не добавлено.
Убран link-loss blackout и для принятых legacy Actors команд, и из AC controller
lease. Продолжаются принятые фейды, анимации, задержки и loop; следующую сцену ESP
не выдумывает. При возвращении получает **текущий** индекс master, не проигрывает
историю. Remote по-прежнему не копит нажатия offline, а истёкшие/чужие команды
не могут активировать выходы после reconnect. Boot/session rotation сохранена.

STOP/ALL_OFF, maintenance и OTA остаются явной остановкой. В AC сохранены
блокировки неисправного Z-C, CPU heartbeat, timing/RMT faults: это корректность
самого драйвера, не реакция на Wi-Fi. Программный STOP не аппаратный разрыв сети.

## Реальная версия firmware

В «Сети» мастер показывает свою полученную `/status.version`, а каждому
slave/remote/helmet добавлена колонка **«Прошивка»** отдельно от версии плана.
Нет подстановки номера master/исходников в данные ведомого. Неизвестно = «—»;
offline = последняя сообщённая версия, не подтверждение текущей связи.

Опциональный64B `FIRMWARE_REPORT` service protocol4 с role/session/deviceBoot/
ASCII version[24]. Новый master помечает DISCOVER как запрос FW1; новые узлы
сообщают версию после HELLO/проверки связи только при этом запросе. Неизвестный
MAC не создаёт actuator-slot из version report. Master проверяет зарегистрированные
MAC/роль/текущие boots/session; новая boot очищает старую версию. R/1 и старые
72/64/100/116B service layouts не переопределяются. Старые producers, не умеющие
этого отчёта, показываются неизвестными. Remote0.7.8 остаётся рабочим по R/1:
обновлять его только ради номера версии необязательно.

## JSON: напоминание и версии файлов

-Optional `Workspace.backup`: major/minor/exportedFingerprint/exportedAt.
 Первая серия1, первый файл `Спектакль_v1.001.json`. Поле **«Серия JSON»** меняет
 только major, новая серия начинается с001; повторная выгрузка тоже увеличивает
 minor. Major автоматически не переключается, minor после999 продолжает1000.
-JSON содержит и draft, и immutable published snapshot, настройки и привязки.
 Не является полным дампом flash/NVS и не включает содержимое SD-карты.
-Подключённый master **атомарно резервирует номер** через token-protected
 POST `/api/console/backup-sequence` и независимый `/backup-sequences.json`.
 Счётчик keyed by project/major, переживает reboot, учитывает floor из JSON/browser;
 два online-клиента не получают один зарезервированный номер. Это не публикация,
 не изменение сцены/навигации. Файл старого проекта не откатывает счётчик.
-Есть browser high-water ledger. Если master недоступен/не может записать счётчик,
 скачивание не блокируется: используется локальный номер, это отмечено в сообщении.
 Между разными одновременно offline-устройствами глобальная уникальность номеров
 не обещается. Ошибочный master journal не очищается молча.
-Через10мин после появления несохранённого **содержимого draft** — небольшой
 **немодальный** prompt «Скачать JSON / Через10мин». Он не перехватывает управление,
 не останавливает исполнение, не вызывает GO. Правки каждые несколько секунд не
 откладывают напоминание бесконечно; фоновые вкладки покажут его при возврате.
-Навигация, пинги, публикационные метаданные, revision/updatedAt и изменение
 файлового номера не считаются правками партитуры. Если содержимое уже выгружено
 или возвращено к нему — напоминания нет. Импорт JSON считается известной копией.
-Receipt/counters сохраняются в browser/master workspace; новый локальный receipt
 не теряется от быстрого закрытия до debounced master-save. Он никогда не заменяет
 более новый draft master. При metadata-only save/publish поля backup сохраняются.
-Browser сообщает о запросе скачивания, но не может доказать завершение системного
 Save dialog или сохранность/неудалённость файла. Резервированный, но не скачанный
 номер допустимо пропустить. Это не автоматическая запись файлов и не cloud upload.
