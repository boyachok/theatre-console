## Роли: счётчик НЕ переносится в пульт

**Master — единственный авторитет шага** и издатель партитуры. Remote отправляет
вперёд/назад/первый/последний; master изменяет step/transition. Веб-плеер «Показ»
меняет тот же счётчик через /api/console/go. Все источники сериализованы controller
задачей, нет отдельного счётчика в пульте/браузере и конкурирующих master.

Пульт не посылает значения каналов и не рассылает сцены напрямую. Для НОВОГО шага
master должен работать. Уже запущенные программы slave/helmet выполняются локально
и продолжаются при обрыве связи/потере master. Это не аварийный останов.

## Публикация и проверяемая готовность

1. Веб компилирует абсолютные cue каждого прибора по MAC; master проверяет/хранит их.
2. STORE214B/score-protocol7 передаёт их фоном; SlaveStore учитывает пропуски,
   проверяет CRC32 полного плана, пишет tmp+rename в `/slave-score.bin`.
3. ACK сохранения связан с MAC, slave boot, версией и CRC именно его плана.
   Подтверждение одного контроллера не подтверждает остальные.
4. До подтверждённой записи ВСЕХ назначенных планов пульт и веб-GO получают
   NOT_READY/409, общий счётчик не меняется. В «Сети» видны загруженные/назначенные.
   Отвергнутое нажатие само не сработает позже, когда загрузка завершится.
   Подтверждённое хранение не гарантирует текущую связь: если уже загруженный узел
   позже временно offline, остальные могут продолжать счётчик; новый шаг для него
   не считается подтверждённым до его ответа.
5. Сохранённый план проверяется при boot, но не включается автоматически. При
   совпадении версии/CRC повтор STORE подтверждает его без полной перезаписи.

Формат cue170B и файла16B+cue сохранён; новые протокол и capability относятся
к доставке/запуску. Непустая повреждённая FS не форматируется автоматически.

## Показ: RUN44B, никаких выходных значений

RUN содержит только version, CRC, step, run/transition, boot/session и служебные
поля. Slave выбирает **локальный** `cues[step]`; все PWM/relay/audio/strip-настройки
берутся из него. Полного cue в RUN больше нет, fallback на старый RUN запрещён.

Несовпадение версии/CRC/числа шагов или отсутствие плана не запускает случайную
сцену: выдаётся NOT_READY/MISSING_PLAN. Master снимает готовность этого узла,
докачивает план и повторяет текущий индекс. Неверный индекс/boot/session/protocol
не меняет выходы. Предыдущая активная программа удерживается по прежней политике.
Дубликаты не перезапускают переход; старые transition не откатывают состояние.
STOP не отменяется повтором того же перехода.

Контрольная сумма — от плана конкретного slave, поэтому одной версии недостаточно.
Номер шага без версии/CRC передавать небезопасно: одинаковый номер мог бы означать
разные состояния после новой публикации.

## Предпросмотр: отдельный PREVIEW214B

С0.7.8 переключатель **«Предпросмотр»** заменяет старый «Пропись/Показ».
ON — явное разрешение исполнения выбранной сцены и её правок. Банк всех draft
шагов хранится в RAM master, обновляется full/patch+revision. Пульт навигирует этот
же банк до публикации; веб/инспектор следуют master stepId/navigation без echo GO.
Выходы идут в PREVIEW, не RUN, опубликованные flash-планы не меняются.

OFF сначала прекращает LIVE, затем автоматически публикует/синхронизирует изменения
в память назначенных контроллеров. Не запускает новую сцену, не откладывает GO;
после readiness нужен новый явный remote/web action. Счётчик сохраняется по ID,
включая новый ещё не опубликованный шаг. Старые локальные программы продолжаются,
это не blackout/STOP. После reboot master LIVE выключен, автозапуска нет.

В OFF правки не исполняются автоматически: immutable publication получает новую
версию, сначала требуется preload ACK всех назначенных. Номер у пульта/веба один,
relative web actions тоже вычисляет master. [Детали/границы](PREVIEW_MODE.md).

## Реальное подтверждение в «Сети»

Для каждого исполнителя: версия сохранённого плана, текущий подтверждённый шаг,
число ответов сцен и статус «Загрузка плана / План готов / Ожидаем ACK /
Применена / Ошибка, не готов / Обновить прошивку».

HTTP200 или успешный udp.send **не создают ACK slave**. «Применена» появляется
только при APPLIED+ACTIVE, нужных run/transition/step и свежем ответе. Старый ACK
не подтверждает новый шаг; старый отрицательный ACK не отменяет более свежий.
Keepalive без целевой сцены не подтверждает старую удерживаемую программу как новую.
Старый boot отбрасывается. После потери свежести подтверждение скрывается.

Это ACK **программного применения/начала исполнения**, НЕ завершение всех фейдов,
задержанных реле или физическая обратная связь лампы/динамика. Для этого нужны
датчики/дополнительный отдельно определённый статус. Ping-ответы не выдаются
за ответы сцен (в таблице это разные счётчики).

## Задержки и надёжность

- Первый пакет нового GO отправляется через ближайший слот, не ждёт повтора.
- Повтор активного состояния **200мс** для каждого контроллера; UI опрашивает
  статус с паузой200мс после ответа. Это резерв после потери, не задержка каждого GO.
- Общий слот отправки всё ещё10мс. В native-тесте10приборов получили первые
  отправки за90мс, каждому повтор через200мс. Это **симуляция планировщика**,
  не RF/физическое измерение. На реальном стенде надо добавить Wi-Fi/loop/выходы.
- В простое heartbeat500мс, STORE по прежнему100мс на узел; загрузка может занять
  время ДО показа. Локальное исполнение каждого fade/кадра от сети не зависит.
- Нет executeAt/общего барьера одновременного старта. При продолжающейся потере
  пакетов конечной гарантии доставки нет. Более короткий RUN уменьшает трафик,
  но не делает Wi-Fi жёстким real-time или системой безопасности.
