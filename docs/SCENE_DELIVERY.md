# Сцены: фактический контракт 0.7.2 / подготовленной0.7.3

## Уже работает

1. Master компилирует отдельный план по MAC для каждого исполнителя.
2. STORE передаёт cue фоном; SlaveStore собирает их с учётом пропусков, проверяет
   CRC32 и сохраняет полный план в `/slave-score.bin` через tmp+rename.
   Это flash, не только RAM. Boot читает сохранённую партитуру без её автозапуска.
3. Master показывает ACK сохранённой версии и ACK текущего перехода отдельно.
4. Slave локально исполняет эффекты, фейды и задержки; сеть не посылает каждый PWM
   отсчёт/кадр/аудиосэмпл. При потере связи активный исполнитель продолжает программу,
   держит достигнутое состояние и согласуется при восстановлении.
5. RUN защищён текущими master/slave boot/session и монотонным transition ID.
   Дубликат не перезапускает программу; ACK повторяется. Это не датчик нагрузки.

## Ещё НЕ реализовано: запуск только по номеру сохранённой сцены

Обсуждавшийся целевой вариант: сначала сохранить планы, затем передавать только
версию/контрольную сумму плана + номер шага + ID перехода; slave выбирает локальный
cue, а при отсутствии нужной версии не исполняет неправильный индекс.

**Фактическая0.7.2 и новая0.7.3 пока передают полный cue в RUN214B**, и Runner
применяет `p.cue`, а не `SlaveStore.cues[p.step]`. Поэтому сохранение уже работает,
но локальный файл ещё не является источником выполняемого RUN. Старт не ждёт,
пока закончится фоновая загрузка всех сцен. Прежнее описание схемы «только номер»
как полностью завершённой было неточным.

В итерации helmet это не исправляется по прямому указанию пользователя
не менять пакетную схему/оптимизацию до тестов. Нельзя незаметно переключить
только один тип slave на локальные индексы: требуется общий контракт версии и
готовности планов, включая preview черновика, восстановление и старые устройства.

## Пульт, master и браузер

Remote не посылает значения яркостей и не хранит партитуру. Он отправляет действия
вперёд/назад/первый/последний master. Master — единственный авторитет текущего шага
опубликованной партитуры, меняет sequence/step и отправляет RUN исполнителям.
**Прямой remote→slave рассылки номера сейчас нет**; при выключенном master пульт
не управляет исполнителями, хотя уже начатые локальные программы продолжаются.

Браузер опрашивает статус master каждые500мс, отображает активный шаг и подтверждения.
Редактируемый/выделенный шаг не равен запущенному. Пульт работает по опубликованной
партитуре; веб-плеер может явно запустить draft-preview. Редактирование само по себе
сцену не запускает. После пульта UI отображает опубликованный активный шаг.

## Интервалы: это не обещание измеренной скорости

- Новый переход сбрасывает nextScore: не ждёт обычных500мс.
- Общий слот RUN/STORE —10мс, unicast по очереди;10исполнителей требуют примерно
  90–100мс только на первую рассылку, плюс loop/Wi-Fi/выходные устройства.
- Текущее состояние повторяется для каждого каждые500мс независимо от ACK.
  После потери первой доставки восстановление поэтому может ждать около500мс;
  при продолжающейся потере пакетов конечной гарантии срока нет.
- У remote своё событие: до4попыток с интервалом120мс, срок700мс; master кеширует
  результат, повтор события не даёт второго шага. Это не повторы RUN исполнителям.
- Нет общего executeAt/синхронизации часов и барьера всех10ACK.
- Реальных измерений latency всех10 одновременно пока нет. Ping RTT одного remote
  не равен времени применения сцены всеми. Нужен отдельный программный замер ACK
  и, для физических выходов, общий триггер/логический анализатор/датчики.

500мс — резервное восстановление, не обязательное ожидание каждого GO и не
частота локальных анимаций. При будущей оптимизации: ускорить подтверждённую
доставку пропустившим slave, не создавать чрезмерный трафик, отдельно решить,
нужна ли синхронность executeAt (она обычно добавляет запас ожидания).
