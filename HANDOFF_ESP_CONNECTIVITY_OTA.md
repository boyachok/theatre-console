## 2. Что подтверждено, а что нет

### Подтверждено

1. Реальные ESP32-S3 определяются как 16 MB flash / 8 MB PSRAM; прошивка DIO/OPI запускается.
2. Мастер 0.6.0 записан по USB, esptool подтвердил hash записанного образа.
3. После записи мастер запустился и подключился к `YOUR_WIFI_SSID`, получил `192.168.50.119`.
4. В последней проверке перед остановкой все восемь ведомых отвечали мастеру по LAN.
   Возраст их отчётов был примерно **57–387 мс**, у всех `protocol=3`.
5. Пользователь сообщил: **«тестовое радио работает»**. Это положительный результат
   пользователя, но не количественный многочасовой протокол испытаний.
6. Обе роли 0.6.0 собираются; host-тесты сетевого кодека, reconnect/DHCP, статистики
   и разделения HTTP/управляющего потока проходят.

### Не подтверждено / не реализовано

- Завершённый end-to-end OTA-переход ведомого с 0.4.1 на 0.6.0 в этой сессии.
- Установленная 0.6.0 на каком-либо реальном ведомом.
- Последовательная раздача firmware мастером всем ведомым.
- Гарантированный real-time, синхронизация часов и локальное расписание событий.
- Длительная проверка всех 10 плат в конечном помещении.
- Точная причина наблюдавшейся пользователем задержки около 3 секунд с телефона.
- Криптографическая аутентификация UDP, подпись firmware, проверка роли образа,
  автоматический rollback или возобновляемая OTA-загрузка.

**Последний запрос на OTA был остановлен пользователем после чтения статуса и
проверки маршрута. Никакого POST с firmware ведомым сделано не было.**
Ранние сообщения чата «нет IP / connected=0» описывают предыдущие этапы; они не
отменяют позднее подтверждённую работающую связь через роутер.

## 3. Оборудование и физические ограничения

- ESP32-S3: Wi-Fi 4, IEEE 802.11 b/g/n, **только 2.4 ГГц**.
- 5 ГГц и Wi-Fi 6 сменой прошивки не добавить. Bluetooth в текущей схеме не используется.
- На проверенных платах встроенный адресный RGB находится на **GPIO48**, используется
  для индикации качества/идентификации. Это не обычный трёхвыводный RGB.
- USB Serial/JTAG, Serial 115200; работающий вариант USB CDC указан в FQBN ниже.
- Порты `/dev/cu.usbmodem...` могут повторяться для разных плат. **Порт не идентификатор.**
- USB-хаб ранее надёжно показывал только одну плату; вторую удавалось подключить напрямую.
- Питание от повербанков может отключаться из-за малой нагрузки: отличать потерю питания от потери радио.
- Целевое помещение: стальные стены примерно 12 мм, несколько этажей, открытый лестничный пролёт.
  Сталь экранирует 2.4 ГГц; связь возможна через проёмы/лестницу/отражения, а не «сквозь сталь».
- ESP-NOW не проникает через металл лучше обычного Wi-Fi, не даёт mesh или ретрансляцию сам по себе.
- При необходимости нескольких AP предпочтителен проводной backhaul. Самостоятельных
  ретрансляторов/mesh в этом проекте нет. Финальное размещение и ориентация антенн ещё требуют проверки.

## 6. Текущая Wi-Fi/LAN-связь

### Подключение

Файл `control/network_config.h`:

```cpp
constexpr char STAGE_WIFI_SSID[]="YOUR_WIFI_SSID";
constexpr char STAGE_WIFI_PASSWORD[]="YOUR_WIFI_PASSWORD";
```

- Мастер и ведомые — **STA-клиенты одного внешнего роутера**, адреса выдаёт DHCP.
- Текущий профиль не создаёт собственную AP `192.168.4.1` и не использует ESP-NOW.
- Канал задаёт роутер, не `RADIO_CHANNEL`. В последнем снимке канал был 10;
  это наблюдение, а не требование всегда использовать 10.
- `WiFi.setSleep(false)`, autoreconnect включён, сохранение Wi-Fi-настроек библиотекой отключено.
- При отсутствии подключения/IP повторная попытка reconnect примерно каждые 10 с.
- При разрыве/IP-change закрывается UDP/mDNS, очищается MAC→IP-кэш, меняется generation.
- UDP после получения IP привязывается заново, не чаще одной попытки bind в секунду.
- mDNS: `stage-master-<последние 3 байта MAC>.local` / `stage-slave-<...>.local`, HTTP80.
  mDNS может не работать между подсетями; наличие имени не заменяет проверку IP.

### Важное исправление MAC в Arduino 3.x

`WiFi.mode(WIFI_STA)` создаёт STA netif асинхронно: слишком раннее чтение могло
вернуть нулевую MAC и hostname `...-000000`. Рабочая последовательность в проекте:

1. `WiFi.mode(WIFI_STA)`;
2. **`WiFi.STA.begin(false)`**;
3. чтение MAC, fallback **`esp_read_mac(mac, ESP_MAC_WIFI_STA)`**;
4. формирование hostname, `WiFi.setHostname(...)`, затем `WiFi.begin(...)`.

Не удалять эту последовательность при переносе кода. Также не возвращать старое
написание SSID `YOUR_WIFI_SSID`: сеть действительно **`YOUR_WIFI_SSID`**.

### Discovery и идентичность

- UDP-порт **4210**. Discovery broadcast вычисляется из DHCP IP и subnet mask,
  а не жёстко задаётся как `.255` для любой сети.
- Мастер рассылает `DISCOVER` каждые 2 с. Ведомые отвечают `HELLO` с задержкой
  примерно 20–369 мс, чтобы не отвечать всем одновременно.
- Мастер 0.6 посылает discovery в двух форматах: protocol4 и legacy protocol3.
- До 10 зарегистрированных ведомых. MAC — стабильная идентичность; IP — текущий маршрут.
- Запоминание MAC/имени: NVS `radio-master`, ключи `mac0/name0` … `mac9/name9`.
  Название namespace историческое, текущий транспорт от этого не становится ESP-NOW.
- MAC→IP в `LanPeers`: 16 записей, обновление по входящим датаграммам, вытеснение
  давно не виденного peer при заполнении. Это оперативный кэш, не статический реестр DHCP.
- Смена IP не должна создавать новую плату. В LAN-конверте есть **MAC назначения**:
  устройство с переиспользованным DHCP-адресом отвергает пакет, адресованный чужой MAC.
- Новый мастер с другой MAC не перехватывает ведомый, пока прежний мастер виден
  в последние 15 с. Проект рассчитан на одного активного мастера, не кластер/failover.
- Очистка статистики не стирает список MAC. Очистка списка сети — отдельная операция:
  удаляет реестр мастера, меняет сессию, очищает маршруты и возобновляет discovery;
  не сбрасывает роутер, SSID/пароль или NVS самих ведомых.

### Wire-формат

`control/lan_wire.h`:

- `LAN_MAGIC=0x34475453`, `LAN_VERSION=1`.
- Packed `LanHeader` **20 байт**: magic, version/reserved, length, source MAC, destination MAC.
- `LAN_MAX_PAYLOAD=100`, но **разрешены только конкретные длины 64 / 72 / 100**.
- Проверяются длина, magic/version/reserved, валидность MAC и адресат; принимается UDP с порта4210.
- Собственные пакеты/пакеты другому адресату отбрасываются.

`control/protocol.h`:

- `MAGIC=0x32544753`, текущий `PROTOCOL=4`, `LEGACY_PROTOCOL=3`.
- Основной `Packet` — **72 байта**, legacy — **64**, `DebugPacket` — **100**.
- Есть дополнительный тип отчёта **64 байта**. Поэтому одной длины64 недостаточно
  для распознавания legacy: декодер также проверяет protocol/type.
- Типы сетевого обмена включают `DISCOVER`, `HELLO`, `PROBE`, `ECHO`, `COMMAND`,
  `COMMAND_ACK`, `IDENTIFY`, `MAINTENANCE`, запросы/отчёты телеметрии.
- Структуры передаются как packed bytes ESP32, не JSON/CBOR и не универсальный сетевой ABI.
  Для другого языка/платформы задавать порядок байтов и размеры явно, сверяться с исходником.
- При изменении сообщений одновременно править структуры, static_assert, LAN whitelist,
  декодеры, совместимость и тесты. Просто увеличить буфер100 недостаточно.

## 7. Надёжность доставки и измерения

- По каждому peer `PROBE/ECHO` примерно раз в **500 мс**, новые отправки разнесены минимум на20мс.
- Нет блокирующего ожидания ответа от конкретного ведомого: пропажа одного не должна останавливать остальных.
- Measurement timeout **400 мс**, дополнительный критерий deadline **100 мс**.
- Отсутствие связи более **3000 мс** считается offline/истечением lease.
- Окно **120 завершённых попыток**, около минуты при штатном темпе. Warmup до20 попыток.
- Метрики: delivery/deadline %, p50/p95/max RTT, p95−p50, текущая/максимальная серия
  таймаутов, поздние ответы, дубли, TX errors, RX drops/invalid, возраст ответа.
- PROBE для измерений не повторяется на прикладном уровне: иначе ретраи скрывали бы качество.
- Пауза измерений **не останавливает heartbeat**. Данные окна/счётчики в RAM;
  JSON с историей содержит ограниченное последнее окно, не бесконечный журнал.
- В LAN RSSI каждого ESP — сигнал **роутера, принятый этим ESP**, не прямая мощность
  ESP→ESP. В ESP-NOW архиве RSSI берётся из принятого радиокадра peer.
- RTT — полный обмен, не односторонняя задержка; делить его пополам для точной синхронизации нельзя.
  В LAN `atUs` ставится при извлечении UDP-пакета, не в Wi-Fi RX callback.

Для подтверждаемых прикладных сообщений уже реализованы общие механизмы:

- ID транзакции, прикладной ACK, дедупликация, возврат cached result при повторе ID.
- Привязка к сессии мастера и идентичности текущего запуска ведомого (`deviceBoot`).
- Случайные ненулевые 32-битные сессии меняются при сетевых переходах; при истечении
  lease идентичность меняется **до разбора накопленных UDP**, чтобы не принять старые сообщения.
- Попытки отправки примерно в 0 / 150 / 300 / 450 мс; после850мс без подтверждения —
  **UNKNOWN: сообщение могло быть исполнено**, а не гарантированная неудача.
- Один pending exchange на ведомый; отдельные сообщения могут его прервать.
- Успешный `udp.endPacket()` или `esp_now_send()` означает постановку на передачу,
  **не подтверждённое принятие удалённым приложением**.

Сессии/MAC/sequence защищают от случайных ошибок и старых пакетов, но не являются
криптографической защитой. Гарантий hard real-time нет. Для точных распределённых
событий отдельно понадобятся clock sync, предзагрузка и политика просроченных сообщений.

## 8. HTTP и управляющий поток в 0.6

`control/control_web.h` — важная переносимая часть, не только обычный WebServer:

- HTTP parsing и ожидания записи в TCP работают в задаче `stage-http`, core0,
  priority1, stack12288.
- Callbacks, которые обращаются к общему состоянию/UDP, передаются через очередь
  в основной `loop()`. Этот поток остаётся владельцем сетевого состояния.
- Ответ callback захватывается в память; собственно отправка HTTP выполняется
  HTTP-задачей. Нельзя снова делать сетевой `send` из callback в основном потоке.
- Пустое спекулятивное TCP-соединение закрывается примерно через100мс, вместо
  стандартного ожидания Arduino до5с. Разбор частичного запроса всё ещё может ждать,
  но в HTTP-задаче, не занимая основной поток.
- Сам callback и `Update.write()` по-прежнему синхронны в основном потоке;
  flash-операции не превращены в полностью неблокирующую систему.
- В сетевой диагностике доступны `serverMs`, `loopGapMaxMs`, задержка прикладного ACK.
- Отдельные HTTP-транзакции имеют deadline и sequence-защиту от поздних запросов;
  это **не глобальный дедлайн доставки UDP и не готовая синхронизация часов**.

Пользователь замечал задержки порядка3с. Потенциальная блокировка старым HTTP
исправлялась, но причина конкретного телефонного наблюдения не измерена.
Успешные mock-тесты не доказывают реальные задержки через конкретный роутер.

## 9. Реально существующий OTA

### Текущий LAN-профиль

Каждая плата имеет собственный HTTP endpoint **порт80**:

- `GET /api/status` — JSON, в том числе `version`, `role`, `mac`, `ip`, `token`.
- `GET /update` — индивидуальная точка входа обновления.
- `POST /update?token=...&target=MAC` — `multipart/form-data`, поле **`firmware`**.
- `target` проверяется, если передан; ошибочная MAC отвергается.
- Token случайный, **на текущую загрузку устройства**; брать заново после reboot.
- Если передан HTTP Origin, он должен совпадать с `http://` + Host.
  CLI без Origin допускается. Это не полноценная авторизация.
- `Update.begin(UPDATE_SIZE_UNKNOWN, U_FLASH)` → `Update.write(...)` → `Update.end(true)`.
- После успешной загрузки ответ `Update OK. Rebooting.`, рестарт примерно через700мс.
- Во время OTA есть режим обслуживания/блокировка неподходящего прикладного трафика.
  Прикладное состояние не должно самопроизвольно возобновляться после перезагрузки.
- Обновляется application в OTA-разделе. NVS не стирается обычной application OTA.

**Допустимый файл — только application `.ino.bin` правильной роли.**
Не загружать merged image, `.bootloader.bin`, `.partitions.bin` или `boot_app0.bin`.
Изменение partition table требует отдельной процедуры/USB, не обычного application OTA.

Важно различать:

- `POST /maintenance` на мастере проверяет свежесть ведомого и возвращает его
  `/update?target=MAC` URL. Это **не проксирование файла и не firmware forwarding**.
- Загрузчик/браузер/CLI должен сам иметь сетевой доступ к **IP ведомого**.
- UDP-доступность ведомого мастером не доказывает, что компьютер может открыть его HTTP.
- HTTP200 от upload ещё не доказывает успешную загрузку нового приложения после reboot.
  Нужны повторная проверка MAC/role/version и возвращение в discovery/heartbeat.

### Чего у master OTA нет

Не реализованы:

- загрузка одного slave bin в мастер с сохранением для дальнейшей раздачи;
- встроенный HTTP-клиент/forwarder firmware на мастере;
- очередь обновлений, update-all, последовательный worker и прогресс по каждой плате;
- подтверждение целевой версии после reboot в составе fleet workflow;
- resume, signed images, проверка master/slave-роли бинарника, automatic rollback.

Наличие двух OTA-разделов само по себе не означает настроенный rollback.
`Update` проверяет допустимость образа в рамках библиотеки, но не роль, доверенный
релиз или криптографическую подлинность. Ошибочным application bin можно прошить не ту роль.

### Безопасный ручной пример отдельной платы

Только для **будущего явно разрешённого обновления**, не запускать вслед за чтением документа.
Сначала подключить компьютер к подходящей LAN/обеспечить маршрут. IP и MAC ниже — пример из снимка.

```bash
cd /Users/boyacheek/Projects/theatre-esp32
./deploy build slave

# Проверить целевую плату ДО POST:
IP=192.168.50.33
EXPECTED=C0:4E:30:27:69:98
curl --fail --show-error --connect-timeout 3 --max-time 5 \
  "http://$IP/api/status" > /tmp/target-esp-status.json

# Проверка роли/MAC, извлечение token именно этой платы:
TOKEN="$(python3 - /tmp/target-esp-status.json "$EXPECTED" <<'PY'
import json,sys
j=json.load(open(sys.argv[1]))
assert j['role']=='slave', 'Wrong role'
assert j['mac'].upper()==sys.argv[2].upper(), 'Wrong MAC'
print(j['token'])
PY
)"

# Перед дальнейшим шагом проверить успешность предыдущих команд и содержимое файла.
curl --fail --show-error --connect-timeout 3 --max-time 120 \
  -F "firmware=@build/control-slave-wifi/control.ino.bin" \
  "http://$IP/update?token=$TOKEN&target=$EXPECTED"

# После reboot повторно получить статус. Если IP изменился — найти плату по MAC
# через актуальный статус мастера. Проверить role=slave и ожидаемую version.
```

Для автоматизации использовать `set -euo pipefail` или явную обработку всех ошибок,
отдельные timeout, журнал MAC→результат и ограниченную политику повторов. При потере
ответа не заливать файл вслепую ещё раз: сначала проверить, не завершилось ли обновление.

### Ограничение существующего deploy ota

```bash
./deploy ota slave IP
./deploy ota master IP
```

Скрипт **сначала каждый раз пересобирает** роль, потом берёт token и отправляет bin.
Сейчас он **не проверяет ожидаемую MAC/role**, не передаёт `target`, не проверяет
версию после перезагрузки. Поэтому это не готовый безопасный fleet updater.
Для нескольких устройств лучше собрать один раз и делать проверенную последовательную загрузку.

## 10. Архивный ESP-NOW и его OTA

Если следующая задача относится именно к прямому радиотесту, а не к LAN:

- `PROFILE=radio`: 0.2.0, protocol2, packet24.
- `PROFILE=espnow`: 0.3.1, protocol3, packet64 / debug100.
- Канал по умолчанию6, допустимы1…11. Все участвующие платы должны совпадать по каналу/профилю.
- `RADIO_CHANNEL` — compile-time настройка; автоматического поиска/переключения/mesh нет.
- ESP-NOW работает через STA interface, peers по MAC, `encrypt=false`.
- RX callback копирует кадр/RSSI и время `esp_timer_get_time()` в FreeRTOS queue;
  обработка вне callback, переполнение учитывается в `rxDrops`.
- Discovery/HELLO, адресные PROBE/ECHO, сохранение MAC-идентичностей, измерение RTT,
  распознавание потерь/дублей присутствуют и в радиопрофиле.
- Ведомый не становится IP-клиентом AP мастера для собственно ESP-NOW обмена.

OTA ESP-NOW-профилей выполняется **НЕ передачей бинарника через ESP-NOW**:

1. У мастера собственная AP `Stage-Master-XXXXXX`.
2. Ведомому отправляется maintenance-запрос; он открывает AP `Stage-Slave-XXXXXX`
   примерно на10мин. Запрос открытия AP сам по себе не является подтверждением загрузки.
3. Подключиться к AP нужной платы, пароль **`debug123`**, адрес **`192.168.4.1`**.
4. Загрузить application bin соответствующего ESP-NOW-профиля через HTTP `/update`.
5. Если радио недоступно, AP обслуживания можно включить USB-командой **`a`**.

AP и ESP-NOW используют одно физическое радио и один канал: не смешивать этот тест
с подключением STA к произвольному роутеру на другом канале.
`debug123`/`192.168.4.1` относятся к архивным профилям, **не к текущему `control`**.
Не переносить старые инструкции из `RADIO.md` на текущую LAN-сборку без адаптации.

Инструменты:

```text

Esptool: 5.3.1

```

Рабочий FQBN:

```text
esp32:esp32:esp32s3:USBMode=hwcdc,CDCOnBoot=cdc,FlashSize=16M,FlashMode=dio,PSRAM=opi,PartitionScheme=custom
```

`./deploy` по умолчанию `PROFILE=control`, роль задаётся compile flag
**`compiler.cpp.extra_flags=-DRADIO_MASTER=1`** или `0`.
Не заменять `build.extra_flags`: ранее это ломало USB macros и давало
`undefined reference to HWCDCSerial`. Сборка `compile --clean`.

```bash
cd /Users/boyacheek/Projects/theatre-esp32
./deploy build master
./deploy build slave

# Только после проверки MAC/назначения подключённой платы:
./deploy master /dev/cu.usbmodem1101
./deploy slave /dev/cu.usbmodemXXXXX

# Архивы:
PROFILE=wifi04 ./deploy build slave
PROFILE=radio RADIO_CHANNEL=6 ./deploy build master
PROFILE=espnow RADIO_CHANNEL=6 ./deploy build slave
```

- `./deploy master|slave` без порта требует ровно одну обнаруженную USB-плату,
  **но не определяет автоматически её роль**. Это не защита от записи slave на master.
- Рабочая flash-настройка **DIO**, не QIO: при QIO наблюдались ошибки ROM-загрузки.
- До записи: **USB reset**, после: **watchdog reset**. Обычный RTS reset иногда
  оставлял S3 в download mode. Esptool baud115200, реальный USB throughput выше UART-оценки.
- Вручную MAC: `esptool --chip esp32s3 --port PORT --before usb-reset --after no-reset read-mac`.
  После `no-reset` плата остаётся в загрузчике: дальше писать с `--before no-reset`
  либо явно вернуть в обычный запуск. Сверить MAC до записи, не просто вывести его в логе.
- Восстановление: держать BOOT → нажать/отпустить RESET → отпустить BOOT → перепроверить порт.
- Успешная запись/hash — ещё не успешный запуск. Проверить Serial `i`/`j` после перезагрузки.
- Python serial: открыть115200, при необходимости **`s.dtr=True`** для native USB CDC.

Диагностические USB-команды текущего профиля: `i` — роль/версия/сеть,
`j` — JSON статуса, `r` — сброс измерительной статистики.
У архивного ESP-NOW дополнительно `a` — AP обслуживания.

### Flash layout

`control/partitions.csv`, разметка16MB:

| Раздел | Offset | Size |
|---|---:|---:|
| nvs | `0x9000` | `0x5000` |
| otadata | `0xe000` | `0x2000` |
| app0 / ota_0 | `0x10000` | `0x600000` — 6 MiB |
| app1 / ota_1 | `0x610000` | `0x600000` — 6 MiB |
| storage / spiffs | `0xc10000` | `0x3f0000` |

При полной USB-записи deploy: bootloader `0x0`, partitions `0x8000`,
core `boot_app0.bin` `0xe000`, application `0x10000`. Обычный deploy не стирает NVS.
Не делать `erase-flash` без отдельного согласования: это уничтожит сохранённые идентичности/данные.
OTA-лимит определяется **6MiB app slot**, не строкой Arduino «Maximum16MB» при компиляции.
Раздел storage объявлен, но готового firmware-cache/fleet storage в приложении нет.

## 14. Если следующая задача — именно master-driven OTA
