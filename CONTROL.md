# 0.6.0 — матрица ON/OFF, настройки PWM на ведомом, 25 кГц

## Выходы

| Функция | GPIO |
|---|---:|
| PWM1–4 | 4 / 5 / 6 / 7 |
| PWM5–8 | 9 / 10 / 11 / 12 |
| Реле ON/OFF | 8 |
| ESP TX → XY RX / ESP RX ← XY TX | 17 / 18 |
| RGB | 48 |

Восемь аппаратных LEDC, 25 кГц, 8 бит, 0–255. Явный XTAL 40 МГц, делитель 6.25.
Частота меняется прошивкой ВЕДОМОГО. На старых 0.4.x/0.5.0 остаётся 1 кГц.
Максимумы при 40 МГц: 8 бит 156250 Гц, 10 бит 39062.5, 12 бит 9765.625,
14 бит 2441.40625. Потолок LEDC не означает пригодность силового модуля.
Проверить переключение MOSFET/нагрев и реальное мерцание/камеру.
Реле GPIO8 не PWM8: PWM8 находится на GPIO12. Электрика: docs/HARDWARE.md.

## Матрица и яркость включения

- `/matrix`: у каждого PWM только ВКЛ / ВЫКЛ, также ВКЛ/ВЫКЛ данного канала всем.
- Все восемь каналов сразу управляемые, никакого назначения/разрешения диммера.
- Настройки выбранного ведомого (⚙): для CH1–8 яркость 0–255 и «Инв.», сохранение ✓.
- Без настройки яркость включения = 255. Значение 0 — допустимая явная настройка:
  логический ON возможен с нулевой яркостью, матрица показывает состояние команды.
- Настройки хранятся в NVS самого ведомого (`stage-io/pwmConfig`), не в мастере.
  Сброс списка сети и перенумерация их не стирают. ON/OFF не пишет flash.
- На главной странице выбранной платы также ВКЛ/ВЫКЛ, яркости редактируются в ⚙.
  Старый API прямого PWM0–255 сохранён для совместимости, но фейдеров в live UI нет.

Отдельный «Диммер PWM»/назначение канала из 0.5 удалены. Это были лишь псевдонимы
PWM, не отдельное оборудование. AC-диммер не реализован, реле не диммируется.

## Инверсия и сохранение текущих состояний

Без инверсии physicalDuty=logicalDuty, с инверсией physicalDuty=255-logicalDuty.
Логический OFF всегда 0, но при инверсии это физический HIGH / duty255.
Внешние подтяжки должны соответствовать безопасному неактивному уровню.

Сохранение PWM-настроек НЕ вызывает ALL_OFF/STOP:
- остальные PWM, реле, очередь/состояние плеера сохраняются;
- ON/OFF редактируемого канала сохраняется;
- изменение яркости включённого канала сразу меняет его уровень;
- изменение только инверсии сохраняет текущую логическую яркость, меняет полярность;
- выключенный канал остаётся выключенным.

Изменение полярности реле на новых ведомых также не обнуляет остальные выходы.
Текущее логическое состояние реле сохраняется; выбор «Не настроено» отпускает
GPIO8 в INPUT и снимает relayOn. Полярность HIGH/LOW автоматически не угадывается.

Это НЕ восстановление нагрузки при перезагрузке: старт и потеря heartbeat = все
логические PWM OFF, реле OFF, STOP. После возврата связи ждём НОВЫЕ команды,
не восстанавливаем уровни/PLAY. ARM и отдельное разрешение плеера не нужны.
UART по-прежнему требует реальных ответов исправного XY-V17B.

## Совместимость

Мастер 0.6 поддерживает 0.4.x (4 PWM) и 0.5.x (8 PWM), но новые сохраняемые presets,
инверсия и сохранение выходов при редактировании требуют ведомого 0.6.
На старых ВКЛ матрицы передаёт обычный PWM255, ВЫКЛ PWM0. UI предлагает обновить
ведомый для новых настроек. Мастер не симулирует сохранение presets у себя.

Для старых 0.4.x ARM/audio-enable выполняются внутри адаптера по ACK. Ограничен
срок подготовки: устаревшая цепочка не запускает отложенный PLAY/PWM. Изменять
полярность старого реле разрешено только при уже выключенных PWM/реле/PLAY,
поскольку старая прошивка сама сбрасывает выходы при DISARM/config. Для изменения
без сброса нужна 0.6. Никакого автоматического восстановления старых нагрузок.

## Задержка, интерфейс и спектакль

В 0.5 ползунок отправлял команду после отпускания, была дополнительная пауза 120 мс
и опрос раз в секунду. Синхронный WebServer работал в цикле UDP/actors; разбор
заголовков/POST мог ждать до 5 с. Это потенциально влияло не только на картинку.
По телефону точный источник наблюдавшихся 3 с пока не установлен.

В 0.6:
- HTTP-разбор и запись в TCP выполняются отдельной задачей, ожидания не занимают
  контроллер. Все callbacks с общим состоянием/UDP/actors исполняются через очередь
  в loop(), ответы копируются/перемещаются и отправляются HTTP-задачей.
- Спекулятивное пустое TCP-соединение занимает сервер не более ~100 мс до закрытия.
- Нажатие сразу показывает «Отправка», нет искусственной паузы 120 мс.
  Опрос 100 мс при ожидании ACK, 500 мс без команд.
- POST /command несёт короткий deadline по времени мастера (UI около 700 мс),
  id+MAC и client+seq. Просроченный HTTP-запрос не выполняется. Старый ON от того
  же клиента не может отменить более новый OFF при перестановке HTTP-запросов.
- При потере HTTP-ответа результат UNKNOWN, а не обещание «не выполнилось».
- HTTP в footer/матрице — время до ответа POST. ACK — от постановки команды на
  мастере до прикладного подтверждения, включая legacy подготовку. Они перекрываются,
  их нельзя просто складывать. Потерянный ACK может прийти позже через ECHO,
  даже если выход уже изменился. ACK ESP не равен началу реального звука.
- `/api/status`: serverMs, loopGapMaxMs и commandAckMs/requestId каждого узла.

Это не жёсткий real-time и не гарантия выполнения за 700 мс: deadline ограничивает
устаревший HTTP/подготовку, но UDP и реальная силовая/аудиочасть требуют измерений.
До обновления ведомых их собственный HTTP всё ещё может блокировать старый цикл.
Для точных спектаклей нужны отдельно загруженные сцены, локальное выполнение и
синхронизация часов. Эти механизмы ещё не реализованы. Проверка реального телефона,
роутера, нагрузки и помещения обязательна; не списывать 3 с только на отображение.

## Сеть, страницы и OTA

YOUR_WIFI_SSID / YOUR_WIFI_PASSWORD, DHCP/mDNS и UDP4210 прежние, MAC — стабильная идентичность.
`/` выбранная плата, `/matrix` сенды, `/diagnostics` метрики/мигание/имена,
`/uart` UART. «Забыть всех / заново» выключает доступные узлы, ждёт 1100 мс,
очищает список/имена мастера и запускает нумерацию заново. Пароль, настройки PWM
и реле на ведомых не стирает. Недоступные узлы полагаются на локальный failsafe.
Браузер помнит выбранный MAC, адресные API требуют id+MAC.

OTA пока ИНДИВИДУАЛЬНАЯ: мастер открывает /update IP выбранного ведомого.
Массовая раздача bin мастером не реализована. Сначала мастер, затем ведомые.
Во время OTA положительные управляющие команды заблокированы до перезагрузки
(либо окончания неуспешной загрузки); OFF/STOP допустимы. Это не ручное ARM.

## Wire и API

Сохранены protocol4 / Packet72 / state32, legacy protocol3 / Packet64 / state24,
debug100 и LAN-конверт20 байт. Добавлен PwmPacket64 с type=PWM_REPORT (11),
session/deviceBoot/uptime и PwmStatus16 (levels[8], inverted, onMask, revision),
frequency и монотонным reportSeq для отбрасывания старых/переставленных отчётов.
Он передаётся после ECHO/COMMAND_ACK; поддержка объявляется 'P'/2 в
метаданных HELLO/ECHO. Старый 'P'/1 содержит только частоту.

POST /command: token,id,mac,op,channel,value,deadline,client,seq.
Старые op3–20 сохранены (1/2/6 внутренние legacy, публично запрещены).
21 PWM_SWITCH: channel1–8, value0/1.
22 PWM_CONFIG: channel1–8, value = level0–255 | (inverted ? 256 : 0).
GET /api/status: pwmConfigSupported, pwmConfig{levels,inverted,onMask,revision},
pwmHz (null если старый производитель не сообщает). Мастер не подставляет 25 кГц
для не обновлённой платы. /dimmer удалён.

## Проверки и установка

Host: GPIO/25 кГц, presets255/0, инверсия, NVS и сохранение других выходов,
нулевой старт/lease, кодеки/совместимость, DHCP и UART. Потоковый mock HTTP
проверяет: зависшая TCP-запись не занимает управляющий поток. Chromium на
390×844 / 375×667 / 320×568: бинарная матрица, настройки, MAC, перенумерация;
запрос, задержанный на 3 с, отвергается без включения PWM.

Мастер A0:85:E3:E2:BC:D4 записан и запущен с 0.6.0, IP192.168.50.119,
имена/список 6 плат сохранены. На момент проверки все ведомые не отвечали.
Ведомая 0.6 собрана, не записана: реальная частота, нагрев, новые presets и задержка
с телефона ещё не проверены на нагрузках. ПК в другой подсети (192.168.0.x),
поэтому его curl к 192.168.50.119 не измеряет телефонный путь через YOUR_WIFI_SSID.

Сборки: build/control-master-wifi/control.ino.bin,
build/control-slave-wifi/control.ino.bin. Команды deploy прежние; архив 0.4.1
PROFILE=wifi04, исходники предыдущей подготовленной 0.5.1 snapshots/control-0.5.1.
Программный failsafe не аппаратный аварийный стоп, UART STOP не гарантирует MUTE.
Админка/OTA/UDP по-прежнему для доверенной LAN, без криптографической аутентификации.
